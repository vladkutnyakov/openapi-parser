# CLAUDE.md

Инструкции для Claude Code при работе с этим репозиторием.

## О проекте

Локальный инструмент для фронтенд-разработки: находит эндпоинт в OpenAPI 3.x спеке и генерирует готовые TS-типы (path/query-параметры, body, ответы, все задействованные DTO с оригинальными именами бэкенда). Плюс режим сравнения своего типа из кода со сгенерированным.

Задача, которую он решает: не переписывать типы из Swagger UI вручную и не сверять контракты глазами, когда бэкенд их меняет.

Существует в двух видах из одной кодовой базы: локальная веб-страница (нужен дев-сервер Vite) и расширение VSCode (панель прямо в редакторе, ничего запускать не надо).

## Команды

```bash
npm run dev        # дев-сервер веб-версии, http://localhost:5173
npm test           # vitest run
npm run test:watch
npm run typecheck  # tsc по всем пакетам
npm run build      # типы + сборка веб-версии
npm run build:vsix # типы + сборка расширения в .vsix
```

Расширение отлаживается через F5 (конфигурация «Расширение: запустить» в `.vscode/launch.json`) — откроется Extension Development Host с командой «OpenAPI Types Tools: Open panel».

**Установку пакетов Claude не выполняет.** При необходимости новой зависимости — правим `package.json` и даём пользователю команду `npm install`, дожидаясь подтверждения перед запуском тестов или сборки.

## Стек

Vite 7 + Vue 3 (`<script setup>`, Composition API) + TypeScript. Тесты — Vitest. Расширение собирается esbuild-ом и пакуется `@vscode/vsce`.

Runtime-зависимостей две, обе у `packages/ui`: Vue и highlight.js (подсветка). У `packages/core` их **ноль** — это осознанно, логика должна оставаться переносимой.

## Архитектура

Монорепа на npm workspaces. Приложение существует в двух оболочках — веб-версия и расширение VSCode, — поэтому общий код вынесен в пакеты, а оболочки оставлены тонкими.

```
packages/core/       @openapi-parser/core — чистый TypeScript, ноль зависимостей
  src/
    openapi-types.ts   подмножество OpenAPI 3.0/3.1
    errors.ts          коды ошибок и SpecError: core не содержит текстов, только коды
    endpoint-index.ts  спека → плоский список эндпоинтов (EndpointEntry.id = "get /users/{id}")
    resolver.ts        разрешение $ref и JSON Pointer
    generator.ts       главный модуль: схемы → блоки TS-кода
    hooks.ts           контракт пользовательских правил, компиляция, изоляция ошибок
    presets.ts         встроенные наборы правил
    ts-parser.ts       разбор вставленного пользователем TS-типа
    type-diff.ts       семантическое сравнение типов
    url-state.ts       состояние навигации в hash URL
    recent-sources.ts  история загруженных источников спек
    find-matches.ts    поиск подстроки: смещения совпадений и шаг по кругу
    node/spec-loader.ts  вход `@openapi-parser/core/node`: загрузка спеки с диска или по URL
  tests/               тесты логики (запускаются из корня)

packages/ui/         @openapi-parser/ui — Vue-компоненты и composables
  src/
    App.vue
    components/        SpecSourceBar, EndpointList, TypeOutput, TypeDiffPanel, HooksEditor
    composables/       useSpec, useHooks, useTheme, useLocale, useUrlState
    i18n/              словари ru/en, типизированный t() (types.ts задаёт форму словаря)
    host/              контракт оболочки: bridge.ts (интерфейс), current.ts (setHost/getHost)
  tests/               паритет словарей локализации

apps/web/            веб-версия: index.html, main.ts, vite.config.ts с middleware /__spec
apps/vscode/         расширение VSCode
  package.nls*.json    переводы строк манифеста (%ключи% в package.json)
  shared/protocol.ts   типы сообщений, общие для обеих половин расширения
  webview/             половина в webview: реализация хоста поверх postMessage, тема, сборка в media/
  extension/src/       половина в Node: activate, панель с CSP, SpecService поверх spec-loader
  esbuild.mjs          сборка extension host в один файл
```

**Зависимости строго в одну сторону: `apps/*` → `ui` → `core`.** `core` не зависит ни от чего, `ui` не знает про приложения. Импорт в обратную сторону — сигнал, что граница протекла.

У `core` в `tsconfig.json` намеренно **нет `DOM` в `lib`**: это машинная гарантия, что в чистую логику не просочится браузерный API. По той же причине у пакета два входа — `.` (работает и в браузере, и в Node) и `./node` (нужен `node:fs`): иначе бандлер веб-версии втянул бы `node:fs` в браузерный бандл.

Тесты живут рядом с логикой (`packages/core/tests/`), но запускаются одной командой из корня — конфиг в `vitest.config.ts`.

### Абстракция хоста

`packages/ui` не знает, где запущен: браузер это или webview VSCode. Всё, что зависит от окружения, объявлено интерфейсом `HostBridge` в `packages/ui/src/host/bridge.ts` — загрузка спеки, сохранение куки, буфер обмена, внешние ссылки, хранилище, **язык окружения**. Реализацию собирает оболочка (`apps/web/src/host-web.ts`) и регистрирует через `setHost()` **до** `createApp`.

В компонентах и composables нельзя обращаться к `localStorage`, `fetch`, `navigator.clipboard`, `navigator.language` и `window.open` напрямую — только через `getHost()` / `hostStorage`. Появление такого вызова в `ui` означает, что абстракция протекла.

**Ленивая инициализация обязательна.** `useTheme`, `useHooks` и `useLocale` держат состояние на уровне модуля. Читать хранилище прямо там нельзя: импорты вычисляются **до** строки `setHost()` в `main.ts`, поэтому чтение вернуло бы пустоту и сбрасывало тему, язык и пользовательские пресеты при каждой загрузке. Поэтому все трое читают хранилище при первом вызове своей функции (флаг `initialized`), а не на этапе модуля.

`hostStorage` намеренно синхронный: асинхронный геттер в эту схему инициализации не встал бы.

### Локализация

Интерфейс существует на русском и английском. Язык определяется автоматически (`navigator.language` в вебе, `vscode.env.language` в расширении), но ручной выбор сильнее и живёт в хранилище под `openapi-parser:locale`.

Переключатель **виден в обеих оболочках**, в отличие от тоггла темы: темой владеет редактор, а язык интерфейса VSCode вполне может не совпадать с тем, на котором человек хочет читать типы.

Своего движка i18n нет и не нужно: ~100 строк и две локали не окупают третью runtime-зависимость. Вместо него — `t()` на ~30 строк в `packages/ui/src/i18n/`.

- **`ru.ts` — источник истины по набору ключей**, `en.ts` типизирован по нему (`types.ts`), поэтому забытый ключ это ошибка `tsc`, а не пустая строка в интерфейсе.
- **Сообщения с подстановкой — функции, а не шаблоны с `{name}`.** Так параметры проверяются типами, а форматтер не нужен вовсе. Вариативный кортеж в сигнатуре `t()` делает параметр обязательным у параметризованных ключей и запрещённым у простых.
- **`t()` можно звать только из шаблона, `computed` или обработчика события.** Он читает `locale.value`, и на этом держится перерисовка: render-функция компонента подписывается на смену языка сама. Обычная `const` на этапе setup вычислится один раз и навсегда останется на языке первого рендера — это самая вероятная регрессия здесь.
- Ключ, собранный в рантайме (`error.${code}`), под вариативный кортеж не подходит — в таких местах `t` приводится к сигнатуре с необязательными параметрами (`useSpec`, `HooksEditor`). Полноту набора ключей взамен проверяет тест.

**Шов перевода.** Переводится только наш текст. Всё, что пришло извне, подставляется как есть: `description`/`summary` из спеки, `statusText` HTTP-ответа, сообщения Node (`ENOENT: …`) и движка JS. Переводится **рамка предложения** вокруг них, а сами данные едут через `params` нетронутыми.

**Сгенерированный TypeScript всегда английский** — он уезжает в чужой репозиторий, и язык интерфейса на него не влияет (`generator.ts`). Тем же правилом объясняется асимметрия: заглушка ошибки генерации в `App.vue` переводится, потому что из панели никуда не уходит.

По той же причине `HookRunner.errors` остаётся готовыми строками с английской рамкой, а не кодами: это отладочный вывод про JS, который пользователь написал сам, и сообщение движка внутри всё равно непереводимо. Коды получают только четыре ошибки `compileHooks`.

### Расширение VSCode

Хостить ничего не нужно: `.vsix` кладёт собранный SPA на диск, панель открывает его в webview, а файлы и сеть берёт на себя extension host — Node-процесс внутри VSCode. Ни порта, ни сервера.

Половины общаются через `postMessage` по схеме запрос/ответ с `id` (`apps/vscode/shared/protocol.ts`). У каждого запроса **обязателен таймаут** (30 с): если обработчик в host упадёт молча, промис в webview зависнет навсегда и UI останется в «Загрузка…». По той же причине роутинг в `panel.ts` целиком обёрнут в `try/catch` с ответом `error`.

**У `loadSpec` ожидание своё и намеренно больше** лимита самой загрузки (`LOAD_SPEC_TIMEOUT_MS` в `protocol.ts`, +5 с в `host-vscode.ts`). Порядок принципиален: сработать должен таймаут загрузчика, который отменяет запрос и объясняет, что молчит **источник**. Ожидание в webview остаётся страховкой от упавшего обработчика — только тогда уместно «Расширение не ответило вовремя». Сравняете лимиты — и медленный бэкенд снова будет выглядеть как поломка расширения.

Константа лежит в `protocol.ts`, а не берётся из `@openapi-parser/core/node`: тот вход тянет `node:fs`, и webview втащил бы его в браузерный бандл.

**CSP панели требует `'unsafe-eval'`** — без него не работает `new Function` в `packages/core/src/hooks.ts`, то есть вся фича правил генерации. Компромисс осознанный: исполняется только код, который пользователь сам написал в редакторе правил, а webview изолирован и от Node API, и от extension host. `'unsafe-inline'` в `style-src` нужен потому, что Vue инжектит `<style>` в рантайме и nonce к ним не приклеить.

**Extension host собирается esbuild-ом в один файл**, а не компилируется `tsc`: он импортирует исходники соседнего пакета через симлинк workspaces, а `vsce` симлинки в `.vsix` не кладёт. Бандл снимает вопрос — в пакет едет только `out/extension.js` и `media/`.

`apps/vscode/package.json` — единственный без `"private": true` (он блокирует `vsce package`) и с `"type": "commonjs"`, перекрывающим ESM корня: VSCode грузит расширение через `require`.

**Упаковка идёт через промежуточную папку `stage/`** (`package-vsix.mjs`). Напрямую из `apps/vscode` паковать нельзя: `vsce` разрешает зависимости по симлинкам workspaces, уходит в корень монорепы и пытается затащить в `.vsix` весь репозиторий — падает на `invalid relative path: extension/../../vitest.config.ts`. Ни `.vscodeignore`, ни перенос пакетов в `devDependencies` этого не лечат: обход идёт до применения игнора. В `stage/` кладутся только бандл, `media/`, README и манифест без зависимостей — симлинков там нет. По той же причине `vsce` зовётся напрямую через `process.execPath`, а не через `npx` (spawn `npx.cmd` из ESM на Windows падает).

Результат — 15 файлов, ~82 КБ. Если в `.vsix` вдруг оказалось заметно больше — значит, обход снова ушёл в корень (признак: файлы вроде `vitest.config.ts`).

Помимо бандла и `media/` в пакет едет витрина Marketplace: `README.md` (описание на странице), `README-RU.md`, `CHANGELOG.md` и `LICENSE` из корня монорепы, плюс `package.nls.json` и `package.nls.ru.json` — переводы строк манифеста. Копируются **без `.catch`** — пропавший файл должен ронять сборку, а не выпускать пакет с пустой вкладкой лицензии или с сырыми `%ключами%` вместо названия команды.

**`.vscodeignore` к попаданию файлов в пакет отношения не имеет**: `vsce` запускается с `cwd: stage/`, а туда копируется только то, что перечислено в `package-vsix.mjs` явно. Забыли `cp` — файла в `.vsix` не будет, и никакой игнор-лист этого не изменит. Полноту ключей охраняет `apps/vscode/tests/nls.test.ts`, он же проверяет, что копирование из скрипта не выпилили. Предупреждение `vsce` про отсутствие `.vscodeignore` в `stage/` ожидаемо: там лежит ровно то, что должно уехать, игнорировать нечего.

Тему панель берёт от редактора: `webview/src/vscode-theme.css` переопределяет переменные приложения на `--vscode-*`. Селектор на `body` (специфичность выше `:root` в `App.vue`), поэтому компоненты не трогаются. Свой тоггл темы в расширении скрыт, `useTheme` там не пишет `data-theme`.

Состояние живёт в `globalState` и приезжает в webview снапшотом прямо в HTML — это и позволяет `hostStorage` оставаться синхронным. Кука авторизации в снапшот **не** попадает: она в `SecretStorage` и в webview не возвращается никогда.

Язык редактора едет **отдельным глобалом** (`ENV_GLOBAL`) рядом со снапшотом, а не внутри него: снапшот — это сохранённый выбор пользователя, и в нём уже лежит ключ `openapi-parser:locale` с ручным переопределением. Запиши мы туда язык хоста, он молча затёр бы выбор при первом же запуске. Обоим глобалам нужно экранирование `<` — это защита от выхода из `</script>`, а не косметика.

**Две точки входа.** Команда из палитры открывает панель с последним источником, кнопка в `editor/title` (видна на любой вкладке) — сразу с файлом этой вкладки, если это файл с диска.

Иконка кнопки — `assets/icon.svg`. Лежит именно в `assets/`, а **не** в `media/`: `media/` — это `outDir` сборки webview с `emptyOutDir`, оттуда иконку стирало бы каждым `npm run build:webview`.

**Иконка рисуется только заливкой (`fill`), без `stroke`.** Это главное: VSCode прогоняет SVG иконок команд через санитайзер, который выбрасывает `stroke`-атрибуты. Контурная иконка после этого остаётся без цвета и рендерится чёрной — независимо от того, что написано в `fill`/`currentColor` и в какой форме объявлено поле `icon`. Скобки и стрелка поэтому нарисованы замкнутыми контурами с заливкой, а не линиями.

Установлено экспериментом: иконка другого расширения (цветная, на чистом `fill`), подставленная в наш манифест, красилась правильно — значит, дело было не в манифесте и не в способе установки, а в самом файле.

Палитра подобрана рендером на реальных фонах Dark+, Light+ и high contrast: `#FFD700` (золотой, как парные скобки в Dark+) не выцветает на белом, в отличие от `#DCDCAA`/`#E5C07B`; стрелка `#4FC1FF` читается на всех фонах, тогда как серая мутнеет на светлом.

**Иконка самого расширения** (список Extensions) — `assets/icon.png`, поле `icon` в манифесте. Только PNG от 128×128: SVG туда `vsce` не принимает. Пересобирается из `assets/icon-source.html` рендером в headless-браузере — отдельного растеризатора в зависимостях нет. Путь подмешивается в снапшот **при рендере**, а не через `globalState.update`: тот асинхронный и не успел бы до чтения снапшота приложением. Активный редактор в команде намеренно не подставляется — иначе вызов из палитры молча подменял бы сохранённый источник на случайный открытый файл.

Панель открывается в `ViewColumn.Beside`: от кнопки на вкладке она иначе встала бы на место самого файла.

### Загрузка спеки

Браузер не может ни читать произвольные пути на диске, ни фетчить чужой бэкенд из-за CORS. Поэтому в `apps/web/vite.config.ts` живёт middleware `GET /__spec?source=<путь-или-URL>`: сервер сам читает файл или скачивает спеку и отдаёт JSON фронту.

Сама логика чтения живёт не в конфиге, а в `packages/core/src/node/spec-loader.ts` — её переиспользует и расширение VSCode. Функция возвращает **структуру** (`ok` / `needs-auth` / `error`), а не HTTP-ответ; middleware переводит её в ответ, extension host — в сообщение.

Ошибка в этой структуре описана **кодом и параметрами, а не текстом** (`packages/core/src/errors.ts`). Код пересекает оба провода — JSON от middleware и `LoadSpecPayload` от extension host — и превращается в сообщение ровно в одном месте, `useSpec.ts`. Иначе не получается: обе оболочки работают в Node и словаря не видят, а положить словарь в `core` значило бы лишить его нулевых зависимостей. В `protocol.ts` поле `code` намеренно типизировано как `string`, а не `SpecErrorCode`: файл общий для двух сборок, и тащить в его граф типы `core` незачем. `readFile` и `fetch` внедряются через параметры, поэтому логика покрыта тестами без поднятия сервера (`packages/core/tests/spec-loader.test.ts`).

**У сетевой загрузки свой таймаут** (`timeoutMs`, по умолчанию 120 с) с `AbortController`: без него запрос к молчащему бэкенду висел бы вечно. Ошибка отдаётся отдельным кодом `source.timeout` с числом секунд, а не общим `technical`, — иначе пользователь видел бы невнятное «This operation was aborted».

Таймер накрывает и **чтение тела**, а не только заголовки: бэкенд может отдать заголовки быстро и замолчать на теле. Промис `r.text()` сам по себе про отмену не знает, поэтому гонится с сигналом явно (`race`) — на этом месте ловится реальный тест, а не гипотеза.

Диск таймаута не касается: `readFile` идёт мимо этой ветки.

**Отмена снаружи** (`signal` в `SpecLoaderDeps`) гасит загрузку наравне с таймаутом, но отдаёт свой код `source.aborted` — иначе смена источника рапортовала бы таймаутом, которого не было. Внешний сигнал переносится на внутренний контроллер вручную, а не через `AbortSignal.any`: у того нет запаса по совместимости.

Подписка на внешний сигнал идёт **до первого `await`**: `getCookie` асинхронный (в расширении это `SecretStorage`), и отмена, пришедшая на этом шаге, иначе осталась бы неуслышанной — запрос уходил бы в сеть с сигналом, который уже некому оборвать. Это ловится тестом.

Путь к файлу резолвится **вызывающей стороной** — загрузчик ждёт готовый абсолютный путь. В расширении относительный путь надо резолвить от корня workspace, иначе он молча указывал бы в папку установки VSCode.

Подключается загрузчик через отдельный вход `@openapi-parser/core/node`. Вход указывает прямо на файл модуля, без промежуточного `index.ts`: `vite.config.ts` грузится Node-загрузчиком напрямую, а тот не разрешает extensionless-реэкспорты внутри барреля.

Middleware вешается на **два** хука: `configureServer` (dev) и `configurePreviewServer` (preview). Без второго `/__spec` в `preview` уходила в статику: SPA-фоллбэк переписывал `req.url` на `/index.html`, браузер кэшировал ответ и получал `304` с пустым телом — а фронт падал на разборе не-JSON.

Регистрировать нужно **в теле хука, а не в возвращаемом post-hook**: post-hook отрабатывает после внутренних middleware, то есть уже после фоллбэка, подменившего URL, — с ним `/__spec` продолжает отдавать HTML. Приложению по-прежнему нужен Node-сервер Vite: чистая статика (nginx, открытый из файла `dist/index.html`) спеки не грузит.

Ответы `/__spec` отдаются с `Cache-Control: no-store` — спека на бэкенде меняется, кэш показывал бы устаревшие типы.

**Смена источника на полпути обрывает предыдущую загрузку.** Кнопка обновления на время загрузки заблокирована, но Enter в строке ввода и выбор из истории — нет, поэтому вторая загрузка поверх первой возможна и запускается штатно.

Защиты две, и обе нужны:

- **Счётчик поколений в `useSpec`** отсекает устаревший результат: побеждает последняя запущенная загрузка, а не ответившая первой. Без него медленный прежний источник молча затирал бы актуальный, а `finally` гасил бы индикатор раньше времени. Счётчик, а не сравнение с `source.value`: пользователь может вернуться к прежнему адресу, и по строке два запроса стали бы неотличимы.
- **`AbortController` рвёт запрос по-настоящему**, чтобы не держать соединение. В вебе сигнал уходит в `fetch`, а middleware ловит `close` на запросе и прекращает тянуть спеку с бэкенда. В расширении `AbortSignal` через `postMessage` не переносится, поэтому отмена едет **отдельным сообщением** `cancel` с id отменяемого запроса, а `panel.ts` держит карту активных загрузок.

Устаревшая загрузка ошибку не показывает: пользователь уже ушёл на другой источник. Поэтому `error.source.aborted` в норме не виден и существует ради полноты словаря.

**Индикация загрузки — три сигнала от одного флага `loading`**, и каждый отвечает на свой вопрос. Вращения иконки в кнопке 34×34 не хватало: она в углу шапки, и смена источника выглядела так, будто ничего не произошло.

- **Полоса неопределённого прогресса** на нижней границе `SpecSourceBar` — периферийный сигнал «идёт работа». Стоит `position: absolute` поверх бордера (`bottom: -1px`), поэтому появление ничего не сдвигает. След дорожки — отдельный `::before` с `opacity`, а не `color-mix` по `--accent`: значение переменной приезжает из темы редактора, и прозрачность поверх готового цвета ведёт себя одинаково в любом движке. Бегунку нужен `position: relative`, иначе `::before` перекрыл бы его.
- **Строка статуса называет источник** (`load.status`) вместо названия прежней спеки. Порядок веток `v-if` значим: ошибка, потом загрузка, потом спека. Без ветки загрузки внизу панели во время смены источника продолжало бы висеть название той спеки, которая уже не имеет отношения к происходящему.
- **Список эндпоинтов гаснет** (`.items--stale`) и перестаёт принимать клики, а при первой загрузке показывает `endpoints.loading` вместо «Загрузите спеку». Иначе видны эндпоинты прежней спеки и непонятно, применилась смена источника или нет. `transition` объявлен на `.items`, а не на `.items--stale`: на модификаторе снятие класса убирало бы и саму плавность, и возврат к рабочему виду шёл бы рывком.

Всем трём нужен `prefers-reduced-motion` — как спиннеру кнопки. Новых токенов темы не заводилось, всё на `--accent` и `--muted`, поэтому в панели VSCode цвета приезжают из темы редактора даром.

### Виртуальный список эндпоинтов

В DOM живёт только видимое окно строк (`EndpointList.vue`). Причина не в прокрутке, а в **ресайзе сайдбара**: его ширина меняется на каждом `pointermove`, и браузер пересчитывает раскладку каждой строки. Замер на спеке в 2000 эндпоинтов: 79 мс на шаг против 1,5 мс после виртуализации — то есть ручка отставала от курсора примерно на 12 кадрах в секунду.

Арифметика окна вынесена в `packages/core/src/virtual-window.ts` и покрыта тестами, в компоненте остаётся только работа с DOM. Ключевой тест — не точечные примеры, а инвариант: на **любой** прокрутке всё видимое попадает в окно.

Что легко сломать:

- **Скроллеру нужны `flex: 1` и `min-height: 0`.** Из его `clientHeight` считается размер окна; без растяжения высота схлопывается под контент, окно выходит меньше экрана, и внизу списка остаётся пустота. Ловится только замером в браузере — тесты арифметики такое пропускают.
- **Падинг живёт на `.sizer`, а не на скроллере.** `clientHeight` включает падинги, а координаты строк отсчитываются от внутреннего края: пока падинг был на `.items`, подкрутка к выбранному эндпоинту недотягивала ровно на его величину.
- **Окно вынуто из потока** (`position: absolute`), иначе его высота складывалась бы с высотой `.sizer` и список прокручивался бы дальше своего конца. Сдвиг — `transform`, а не `top`: он уезжает в композитор и не вызывает перекомпоновку на каждом кадре.
- **Высота строки измеряется, а не зашита константой**: в панели VSCode шрифт приезжает из темы редактора. До первого замера рисуется одна строка — иначе замкнутый круг: окно пустое, и мерить нечего.
- **Подкрутка к выбранному считается арифметикой** (`scrollTopForIndex`), а не `scrollIntoView`: строки восстановленного из URL эндпоинта в DOM может не быть вовсе.
- **Смена фильтра сбрасывает прокрутку**: иначе поиск в прокрученном списке открывался бы посередине, а при коротком результате — на пустом месте.

**Закрытые авторизацией спеки.** Серверный `fetch` идёт без браузерной сессии, поэтому Keycloak отвечает `302` на форму логина. Стоит `redirect: 'manual'`: без него fetch молча прошёл бы по редиректу и вернул HTML со статусом 200 — пользователь увидел бы «невалидный JSON» вместо «нужен вход». Как «требуется авторизация» распознаются: **любой** 3xx с заголовком `Location` (origin'ы при этом не сравниваются), `401/403` и HTML вместо JSON при статусе 200. Фронт показывает ссылку на вход и поле для куки.

Где лежит кука, зависит от оболочки: в вебе она уходит в `POST /__spec/auth` и живёт в `Map` в памяти процесса Vite (перезапуск сервера её забывает), в расширении — в `SecretStorage`. В localStorage она не попадает ни в одном случае: сессионный секрет не должен оставаться в браузерном хранилище.

На практике проверено, что у типичного Spring-бэкенда за Keycloak закрыт только Swagger UI, а сам `/v3/api-docs` отдаётся свободно — то есть ветка с кукой срабатывает редко. Она оставлена ради других бэкендов и покрыта тестами.

### Генератор

`generateBlocks(spec, entry, hooks?)` возвращает массив блоков `{ name, code, kind?, meta? }` — каждый интерфейс или тип отдельно, чтобы у каждого в UI была своя кнопка копирования. `stripComments()` убирает комментарии для копирования в проект: генератор всегда кладёт `//` и однострочные `/** */` на отдельные строки, поэтому построчная фильтрация надёжна.

**`meta` — факты об эндпоинте, а не код** (`BlockMeta`: `method`/`path`/`summary` у заголовка, `status`/`description`/`contentType`/`otherContentTypes`/`noBody` у тел и ответов). Раньше это были комментарии внутри `code`, и там они не читались: адрес, статус и Content-Type подсвечивались тем же тусклым цветом, что и описания полей, и терялись в потоке TypeScript. Теперь их рисует UI своими средствами — заголовок, бейдж, подпись у блока, — а в коде остаются только комментарии, объясняющие сам тип: имена полей и DTO.

Следствия, которые легко нарушить:

- **В `code` метаданные не дублируются.** Проверять их надо по `meta`, а не подстрокой в коде (`b.meta?.status === '204'`, не `b.code.includes('// 204')`).
- **Блоки без кода теперь существуют**: заголовок эндпоинта и ответ без тела несут `code: ''`. Всё, что склеивает или подсвечивает код, обязано их отфильтровать (`generateForEndpoint`, `view` и `v-if="b.html"` в `TypeOutput.vue`) — иначе в выводе появятся пустые строки, а `hljs.highlight('')` отработает вхолостую.
- **`stripComments` метаданных больше не касается** — в чужой репозиторий и так уезжает чистый тип.
- Значения из спеки (`summary`, `description` ответа, ключи content) **не переводятся**: переводится только рамка вокруг них (`output.contentType*`, `output.noResponseBody`).

**`kind` — категория блока** (`TypeKind` из `hooks.ts`: `path`/`query`/`body`/`response`/`dto`), по ней UI группирует вывод в секции. На текст кода поле не влияет — это описание блока, а не параметр генерации. Проставляется в местах создания блоков, где категория и так известна (она рядом уходит в хук `typeName`). Два следствия:

- **UI обязан брать категорию из `kind`, а не разбирать имя.** Хук `typeName` может переименовать блок любого вида, и эвристика по суффиксу `PathParams` рассыпалась бы у пользователя с пресетом.
- **Заголовок эндпоинта — единственный блок без `kind`**: он не относится ни к одной секции. А вот «ответ без тела» (`204`, `name: null`, `meta.noBody`) категорию получает, иначе выпал бы из секции ответов — то есть ровно оттуда, где пользователь ищет этот факт.

**Дефолты — классический TypeScript**: необязательные поля через `?`, enum как union строковых литералов, точки с запятой в конце строк и у алиасов. Конвенции конкретного бэкенда (в ответах `| null` вместо `?`, query всегда nullable, строковый enum → `string`, без `;`) в коде не зашиты вовсе — их задаёт пользователь своими хуками (см. [HOOKS.md](HOOKS.md)).

Важные внутренние решения:

- **`PropStyle`** (`'optional' | 'nullable'`) на вывод по умолчанию не влияет — оба стиля дают `field?: T`. Он нужен, чтобы передать хукам `source` (`'response' | 'body'`) и дать им различать ответы и запросы — на этом строятся пользовательские правила вроде «в ответах `| null` вместо `?`».
- **Апгрейд стиля DTO.** Если один DTO используется и в body, и в response, побеждает response-стиль. Ссылки дообходятся (`pendingWalk`) **до** эмиссии кода — иначе DTO, отрисованный раньше апгрейда, получил бы `source: 'body'` и хук применил бы к нему конвенции запроса.
- **Циклические ссылки** допустимы: интерфейсы ссылаются друг на друга по имени, глубина ограничена `MAX_DEPTH`.
- Имена DTO берутся из `components/schemas` как есть; невалидные идентификаторы (`PageDto«UserDto»` от springfox) санитизируются.
- **У тела запроса и у каждого ответа в `meta` лежит `contentType`.** Тип из спеки выбирает `pickJsonMedia` (JSON в приоритете, дальше `*/*`, дальше первый попавшийся), и по сгенерированному TS отличить `multipart/form-data` от обычного JSON было невозможно — а от этого зависит, как фронт вообще отправляет запрос. Поэтому `pickJsonMedia` возвращает **ключ вместе с объектом** (`PickedMedia`), а не один `MediaTypeObject`.

  Поле заполняется **всегда, а не только у не-JSON**: молчание читалось бы как «обычный JSON», то есть ровно как подпись — и различить эти два случая было бы нельзя. Остальные типы контента едут рядом в `otherContentTypes`: тип сгенерирован ровно по одному из них, и пользователь должен видеть, что выбор был.

### Сравнение типов

`ts-parser.ts` — рукописный парсер (компилятор TypeScript в бандл не тянем). Сравнение семантическое, а не текстовое: `normalizeType` приводит типы к каноничному виду, поэтому порядок полей, форматирование, точки с запятой, кавычки и порядок членов union отличиями не считаются. При этом сравнение строгое: `?:` и `| null` — разные вещи.

Два режима вывода: `diffTypes` (список по полям) и `diffLines` (построчный diff в стиле GitHub).

### Секции вывода

Блоки в `TypeOutput.vue` сгруппированы по `kind` в сворачиваемые секции (path-параметры, query-параметры, тело запроса, ответы, DTO) — иначе у эндпоинта с десятком транзитивных DTO вывод превращается в стену кода. Порядок секций — порядок первого появления категории, то есть порядок генератора; пустых секций не бывает.

- **`kind` и `meta` надо тащить через `view`.** Этот `computed` — узкое место: он оставляет от блока только `name`/`kind`/`meta`/`html`/`copy`, и чего там нет, для шаблона не существует.
- **Метаданные рисуются интерфейсом, а не подсветкой кода.** Заголовок эндпоинта — `<header class="endpoint">` в липкой `.toolbar` рядом с иконкой «Копировать всё», чтобы при прокрутке было видно, чьи это типы (метод бейджем и путь моноширинным — первой строкой `.endpoint-line`, `summary` приглушённо — второй; обе строки не переносятся, а обрезаются многоточием). Цвет метода — глобальный `.method-badge` в `App.vue`, общий с сайдбаром и намеренно не зависящий от темы. Статус ответа и Content-Type — строка `.block-meta` над блоком. Цвета берутся из тех же переменных `App.vue`, новых токенов не заводилось, поэтому в панели VSCode всё приезжает из темы редактора даром.
- **Названия секций хранятся ключами сообщений** (`SECTION_KEY: Record<TypeKind, MessageKey>`), а не результатами `t()`: карта лежит на уровне модуля, и готовые строки навсегда остались бы на языке первого рендера. Резолвится ключ в шаблоне. `Record` по `TypeKind`, а не конкатенация `output.section${kind}`, — новая категория в `core` станет ошибкой `tsc` здесь, а не пустым заголовком у пользователя.
- **Свёрнутое состояние хранится по категории, а не по эндпоинту** (`openapi-parser:sections-collapsed`): свернувший DTO хочет, чтобы они остались свёрнутыми и на следующем эндпоинте. В хранилище лежит список **свёрнутых** — по умолчанию раскрыто всё, и битое значение даёт то же самое.
- **Цвет категории живёт только в полосе слева** и берётся из переменных `App.vue` (`--accent`, `--warning`, `--success`, `--danger`, `--muted`). Новых токенов не заводилось — поэтому в панели VSCode цвета приезжают из темы редактора даром.
- **Заголовок секции липкий** (`position: sticky` под `.toolbar`): в длинной секции DTO должно быть видно категорию и доступны свернуть/скопировать. Отступ `top` — переменная `--toolbar-h`, которую **меряет `ResizeObserver`**, а не токен: в панели VSCode шрифт из темы редактора. Два следствия: `scrollRangeIntoView` вычитает и высоту заголовка секции (иначе совпадение прячется под ним), а сворачивание прилипшей секции (`onSectionToggle`) возвращает её заголовок на место — иначе при прежнем `scrollTop` под курсором оказывалось бы случайное место следующих секций.
- Заголовок секции и кнопка копирования секции — **две кнопки-соседа, а не вложенные**: кнопка внутри кнопки невалидна, и скринридер такую вложенность схлопывает.

### Поиск по сгенерированным типам

Ctrl+F в панели вывода: строка поиска, подсветка всех совпадений, счётчик, Enter/Shift+Enter по кругу, Esc. Поиск литеральный и без учёта регистра, тумблеров регистра и regex нет.

Подсветка рисуется **CSS Custom Highlight API**, а не вставкой `<mark>` в HTML. Причина: содержимое блока — уже готовая разметка highlight.js с сущностями (`&lt;`, `&gt;`, `&#x27;`), а в типах полно `<`, `>`, `'`. Переписывание такой строки требует карты «смещение в тексте → смещение в HTML», и любая ошибка в ней молча разрезает сущность пополам; вдобавок каждое нажатие Enter пересобирало бы `v-html` целиком. Вместо этого из смещений строятся `Range` поверх уже отрисованных текстовых узлов, и разметка hljs не трогается вовсе.

Что из этого следует:

- **Совпадение, пересекающее границы токенов, работает само.** Запрос `Dto>` — где `Dto` внутри `<span class="hljs-title">`, а `>` снаружи — для `Range` обычный случай.
- **Правила `::highlight()` живут в глобальном `<style>` `App.vue`, а не в `<style scoped>` компонента.** Scoped-стили работают через дописывание атрибута `[data-v-*]`, а подсветка — не элемент: дописывать не к чему, и правило не совпало бы никогда. Из свойств задаётся только `background-color` — `text-decoration` и `text-shadow` Firefox в подсветках игнорирует.
- **Реестр подсветок глобальный на документ**, поэтому имена с префиксом (`openapi-find`), а `onBeforeUnmount` обязан их удалять.
- **Индексируется каждый блок отдельно**: так совпадение, сшитое через границу двух несвязанных типов, невозможно в принципе.
- **`v-html` пересоздаёт поддерево при смене эндпоинта**, и собранные `Range` указывают на оторванные узлы — отсюда пересборка по `watch([view, query, findOpen])`.
- **Перехват сравнивает `e.code === 'KeyF'`, а не `e.key`**: на русской раскладке Ctrl+F даёт `key === 'а'`, и поиск молча перестал бы открываться ровно там, где им пользуются.
- Ctrl+F **не перехватывается** в полях ввода (там его отдаём браузеру), при открытом редакторе правил и когда типов ещё нет. Если `CSS.highlights` в движке отсутствует, перехвата нет вовсе — открывается штатный поиск браузера, и это верная деградация.
- Открытость редактора правил лежит в `useHooksEditor`, а не приходит пропом: это факт уровня приложения, а проверка `e.target` не годится — после клика по фону модалки `target` это `<body>`, и перехват сработал бы всё равно.
- **Свёрнутые секции скрыты `v-show`, а не `v-if`.** `rebuildHighlights` обходит `pre.code` в DOM: с `v-if` узлов там нет, и совпадения в свёрнутой секции молча терялись бы — счётчик врал бы пользователю. Шаг к совпадению внутри свёрнутой секции её **разворачивает** (`revealSection`), после чего `scrollRangeIntoView` зовётся через `await nextTick()`: у скрытого узла `getBoundingClientRect` даёт нули, и подкрутка молча не сработала бы.

**Текущее совпадение выбирается от якоря**, а не первым во всём выводе (`anchoredMatchIndex`): иначе поиск поля в нижней DTO на каждую букву уносил бы панель к верхним. Якорь — прежнее текущее совпадение, если его `Range` ещё в документе (`isConnected`): это правка запроса, DOM тот же, и допечатка буквы не сдвигает с места. Иначе — верх видимой области под `.toolbar`: поиск только открыли, сменился эндпоинт (`v-html` оторвал старые узлы) или сменилась область. У совпадения в свёрнутой секции рамка нулевая, поэтому для него сравнивается рамка `.section` — без этого оно считалось бы «выше экрана» даже внизу вывода.

**Область поиска — один блок.** Ctrl+F после клика внутри блока ограничивает поиск им (чип «в UserDto ×» в `FindBar`, обводка `.block--scoped`); клик мимо блоков — поиск по всему выводу. Повторный Ctrl+F при открытом виджете переключает область на блок последнего клика. Что важно:

- **Клики внутри `.find-bar` блок не перезаписывают** — иначе повторный Ctrl+F из поля поиска сбрасывал бы только что заданную область.
- **Область хранится по имени блока (`data-name`), а не по индексу**: та же DTO на соседнем эндпоинте остаётся областью. Если блока с таким именем нет — область снимается сама, а не оставляет пользователя с «Нет совпадений».
- Закрытие поиска область сбрасывает, запрос — нет.

Чистая часть (поиск смещений, шаг с заворотом, выбор от якоря) — в `packages/core/src/find-matches.ts` и покрыта тестами; в UI остаётся только работа с DOM.

### Состояние

Всё состояние идёт через `hostStorage`; где оно физически лежит, решает оболочка — localStorage в вебе, `globalState` в расширении.

- **Навигация** (выбранный эндпоинт, поиск, фильтр по методу) — **в вебе** в hash URL: переживает F5, работают «назад/вперёд», ссылкой можно поделиться. Набор текста пишется через `replaceState`, смена эндпоинта — через `pushState`, иначе история засорялась бы отдельным шагом на каждую букву. **В расширении** hash бесполезен (панель не переживает закрытия, «назад» ведёт себя не как в браузере), поэтому то же состояние складывается в хранилище под ключом `openapi-parser:nav`.
- **Хранилище** — источник спеки, история источников, тема, язык, ширина сайдбара, режим диффа, свёрнутые секции вывода, пресеты правил (10 ключей с префиксом `openapi-parser:`).
- **История источников** (`openapi-parser:recent-sources`) — JSON-массив записей `{ source, name? }`: путь или URL, который уже успешно загружался, плюс необязательное название, заданное пользователем вручную. Логика списка (добавление, поднятие наверх вместо дубля, лимит, переименование, фильтрация для автокомплита, разбор битого значения) вынесена в `packages/core/src/recent-sources.ts` и покрыта тестами; UI только хранит результат через `hostStorage`. В историю пишется **только успешная** загрузка — иначе список забивался бы опечатками. Работает и в вебе, и в расширении: ключ обычный, поэтому в панели VSCode он приезжает снапшотом из `globalState` без отдельной поддержки.

  Важные решения:

  - **Парсер понимает и старый формат — массив строк.** История, накопленная до появления названий, иначе молча обнулилась бы при обновлении.
  - **`addRecentSource` не стирает заданное название**: повторная загрузка того же источника поднимает запись наверх вместе с её именем.
  - **Пустое название снимает поле `name` совсем** (а не сохраняет пустую строку) — иначе пользователь не смог бы вернуться к показу одного пути.
  - История показывается **выпадающим списком под строкой ввода** (`SpecSourceBar.vue`), а не по кнопке: список открывается по фокусу и по набору текста, фильтруется подстрокой по пути **и** по названию, ходится с клавиатуры (↑/↓/Enter/Esc). Фильтр намеренно считает запрос пустым, когда в строке ввода стоит ровно один из известных источников: иначе при открытии панели с уже загруженной спекой список сжимался бы до одной записи вместо всей истории. Индекс `-1` («ничего не выбрано») остаётся достижимым стрелками — так пользователь возвращается к своему тексту. Удаление записи список **не** закрывает: чистят обычно несколько подряд.
  - Переименование — инлайн, прямо в строке списка; `closeList()` сбрасывает и незакоммиченный черновик имени.

## Правила генерации (хуки)

Конвенции вывода не зашиты в код: пользователь может задать свои через JS-хуки (`field`, `scalar`, `typeName`, `declaration`, `docs`), которые вызываются из генератора и переопределяют поведение по умолчанию.

**Контракт хуков, их контексты, примеры и правила написания скриптов — в [HOOKS.md](HOOKS.md).** Этот файл нужно читать перед любыми правками `packages/core/src/hooks.ts`, `packages/core/src/presets.ts`, `packages/ui/src/components/HooksEditor.vue` или точек вызова хуков в `packages/core/src/generator.ts`, и обновлять его синхронно с изменением контракта.

Ключевое правило при работе с генератором: **хук получает «чистый» тип, без `?` и `| null`; конвенции по умолчанию живут только в fallback-ветке.** Если зашить конвенцию в сам тип до вызова хука, пользователь не сможет её отменить.

Ошибки пользовательского кода изолированы `HookRunner`: исключение внутри хука не роняет генерацию — берётся значение по умолчанию, сообщение дедуплицируется, после 20 ошибок хуки глушатся до следующей правки.

**Встроенные пресеты зависят от языка.** `builtinPresets(locale)` и `defaultPresetCode(locale)` отдают код с комментариями на нужном языке; имена встроенных — не текст, а **ключи сообщений** (`preset.classic.name`), которые резолвит `ui` по флагу `builtin`. У пользовательских пресетов в `name` лежит готовое имя, и трогать его нельзя.

`id` между локалями стабильны, поэтому сохранённый `activeId` переживает переключение языка, а вывод генератора не меняется — переводятся только комментарии. Это охраняет тест кросс-локальной эквивалентности; ослаблять его нельзя.

Смена языка переписывает код активного встроенного пресета, поэтому `HooksEditor` **отменяет отложенную запись** (`watch(locale, () => clearTimeout(debounceTimer))`): иначе таймер сохранил бы текст на старом языке и задним числом форкнул пользовательскую копию.

## Конвенции кода

- Комментарии — на русском, по делу: объясняют **почему**, а не пересказывают код. Плотность как в существующих файлах — комментируются неочевидные решения, а не каждая функция.
- **Пользовательских строк-литералов в компонентах `packages/ui` быть не должно** — только `t()`. А `packages/core` прозы не содержит вовсе, лишь коды ошибок; единственное исключение — английский комментарий в сгенерированном коде (`generator.ts`).
- Точки с запятой в исходниках проекта используются.
- Любая логика, которую можно проверить без DOM, живёт в `packages/core/` и покрывается тестами.
- Vue-компоненты: `<script setup lang="ts">`, `defineModel` для двусторонних привязок, состояние — через composables.
- Ошибки не должны ронять приложение: невалидная спека, битая ссылка в URL, сломанный хук, недоступное хранилище, молчащий extension host — везде graceful degradation с понятным сообщением. Обработка недоступного хранилища живёт в реализации хоста, а не в компонентах: `host-web.ts` глушит исключения localStorage, а `hostStorage` отдаёт `null`, если его вызвали до `setHost()`.

## Темы

Обе темы (тёмная/светлая) обязательны для любого нового UI. Цвета берутся **только** из CSS-переменных, объявленных в `App.vue` (`--bg`, `--panel`, `--border`, `--text`, `--muted`, `--accent`, `--danger`, `--success`, `--warning`, `--diff-add-bg`, `--diff-del-bg`, `--hover`, `--selected`, `--find-match-bg`, `--find-match-active-bg` и токены подсветки `--hl-*`). Захардкоженных цветов в компонентах быть не должно.

Это правило теперь работает и на расширение: `apps/vscode/webview/src/vscode-theme.css` переопределяет **тот же набор** переменных на `--vscode-*`. Заводя новую переменную, добавьте её в оба места — иначе в панели цвет останется от веб-палитры и не переключится вместе с редактором.

Подсветка кода использует свои стили токенов на этих переменных, а не готовые темы highlight.js — иначе код не переключался бы вместе с темой.

**Подсветка в расширении совпадает с редактором точно.** Цвета токенов (`tokenColors` темы) в webview переменными `--vscode-*` **не пробрасываются** — туда попадают только зарегистрированные theme colors, а Textmate-скоупы к ним не относятся. Обходной путь через `--vscode-symbolIcon-*` не работает: стоковые темы этих цветов не задают, они приходят из дефолтов реестра и с палитрой подсветки не связаны.

Поэтому JSON активной темы читает extension host (`extension/src/theme-service.ts`) и вкладывает семь цветов блоком `<style>` прямо в HTML панели — не сообщением, иначе первый кадр мигал бы веб-палитрой. Разбор темы вынесен в `extension/src/theme-tokens.ts`: он не импортирует `vscode` и покрыт тестами (`apps/vscode/tests/`, поэтому `vitest.config.ts` включает и `apps/*/tests/`).

Что важно помнить при правках:

- **Цепочку `include` надо разворачивать.** Она бывает глубже одного шага (`dark_modern` → `dark_plus` → `dark_vs`), а у производной темы своих `tokenColors` может не быть вовсе — без склейки такая тема дала бы пустой результат. Базовая идёт первой, производная её перекрывает.
- **Скоупы матчатся префиксно**, как в Textmate: правило `comment` покрывает `comment.line.double-slash`. Порядок скоупов в `SCOPES` — по убыванию точности, и он значим: в Dark+ `variable` и `entity.name.type` разного цвета.
- **Файлы тем — JSONC**, с комментариями и висячими запятыми; `JSON.parse` их не берёт, поэтому в `theme-tokens.ts` лежит свой `parseJsonc`. Запятые он срезает в том же посимвольном проходе, а не регуляркой по готовой строке: регулярка съедала бы запятую внутри строкового литерала.
- `editor.tokenColorCustomizations` накладывается поверх темы — иначе панель расходилась бы с редактором именно там, где пользователь настроил цвета руками.
- Неразобранная тема (например, `.tmTheme` в plist) — не ошибка: блок `<style>` не выводится, подсветка остаётся на палитре из `App.vue`.

Смена темы перерисовывает HTML панели (`onDidChangeActiveColorTheme`): цвета вшиты в разметку. Состояние это переживает — оно в `globalState` и снапшоте.

Кнопкам с текстовыми иконками нужно явно задавать `color` — без него символ берёт чёрный цвет браузера по умолчанию и пропадает в тёмной теме (эмодзи такого не показывают, так как раскрашены сами).

## Тесты

`packages/core/tests/` — generator, hooks, type-diff, url-state, spec-loader, recent-sources, find-matches, virtual-window; `packages/ui/tests/` — паритет словарей локализации; `apps/vscode/tests/` — разбор тем VSCode и полнота `package.nls*.json` (всего 224 теста). Логика в `core` тестируется напрямую, компоненты не тестируются.

Для генератора есть фикстура `packages/core/tests/fixtures/sample-spec.json` в стиле типичного Spring-бэкенда: `$ref`, enum, `allOf`, `nullable`, вложенные DTO, циклическая ссылка, DTO одновременно в body и response, тело с двумя типами контента (`multipart/form-data` + `application/octet-stream`), query-параметр с ключом-не-идентификатором (`filterDto.id`).

Три теста охраняют важные инварианты — их нельзя ослаблять:

- **round-trip** (`type-diff.test.ts`): каждый сгенерированный блок, вставленный обратно в сравнение, даёт «типы совпадают»;
- **образец `defaultPresetCode(locale)` воспроизводит поведение по умолчанию** (`hooks.test.ts`, describe «пресеты»): код-образец в редакторе даёт тот же вывод, что и генератор без хуков — проверяется **на каждом языке**. Это гарантирует, что документация в образце не расходится с реальными дефолтами;
- **встроенные пресеты дают одинаковый вывод на обоих языках** (`hooks.test.ts`): у локалей отличаются только комментарии. Если правка перевода залезла в поведение, вывод разойдётся — и это поймается здесь, а не у пользователя.

После правок обязательно `npm test` и `npm run build`.

Важно: `vite build` **сам по себе типы не проверяет** — их проверяет отдельный шаг `npm run typecheck`, который `npm run build` запускает первым. Если менять сборку, эту связку нельзя терять, иначе ошибки типов уедут в рантайм.
